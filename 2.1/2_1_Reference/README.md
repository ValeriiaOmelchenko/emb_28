# Еталон 2.1 - Embedded C++ на ESP32: blink без delay(), режими кнопкою, вимірювання superloop

Плата ESP32-S3-DevKitC-1, фреймворк Arduino (PlatformIO). Стиль процедурний: `struct` + функції, `enum class`, `constexpr`, `static` на рівні файлу. Без класів, без `new`/`malloc`, без `String` і STL-контейнерів.

## Схема

```
GPIO 4 ──[270 Ом]──▶|── GND        LED червоний (анод, довга ніжка, до резистора)

GPIO 7 ──┤ кнопка ├── GND          внутрішній pull-up, натиснута = LOW
```

| Компонент | GPIO | Чому цей пін |
|---|---|---|
| LED + 270 Ом | 4 | не strapping (0, 3, 45, 46), не USB (19, 20), не флеш/PSRAM (26-37) |
| Тактова кнопка | 7 | те саме; ніжки беремо по діагоналі (ніжки однієї пари замкнені завжди) |

Без зовнішньої кнопки можна взяти BOOT (GPIO 0, на платі вже є підтяжка 10 кОм): `BUTTON_PIN = 0`. Але не тримати її під час ресету, бо це strapping-пін і плата стартує в режимі прошивки.

## Розрахунок резистора

Від 3,3 В, а не від 5 В. Ціль ~5 мА, цього достатньо для індикації:

```
R = (3,3 - Vf) / I = (3,3 - 2,0) / 0,005 = 260 Ом → E24: 270 Ом, I ≈ 4,8 мА   (червоний)
R = (3,3 - 3,0) / 0,005 = 60 Ом → E24: 68 Ом, I ≈ 4,4 мА                      (синій / білий / «чистий» зелений)
```

Vf краще поміряти на своєму LED (урок 1.2). У синього з «універсальними» 220 Ом буде лише ~1,4 мА, і він ледь світитиме.

## Як запустити

```bash
pio run -t upload && pio device monitor
```

## Вивід

```
Еталон 2.1: кнопка перемикає Блимання → Увімкнено → Вимкнено
loop(): середнє ... нс, макс ... мкс (блок 1000 ітерацій)
Режим: Постійно увімкнено (викликів ISR від минулого натискання: 1)
Режим: Постійно вимкнено (викликів ISR від минулого натискання: 1)
Режим: Блимання (викликів ISR від минулого натискання: 2)
```

Це формат виводу. Конкретні числа треба взяти зі своєї плати: середнє - порядку одиниць мікросекунд і менше, максимум помітно більший за середнє. Лічильник викликів ISR має бути 1, зрідка 2-3. Без відключення переривання на тій самій кнопці там були б десятки (див. «Антибрязкіт: відключаємо переривання»).

## Відповідність умові

| Пункт умови | Де в коді | Як зроблено |
|---|---|---|
| 1. `enum class` для стану LED | `led.h` | `enum class LedState : uint8_t { Off, On }` |
| 1. `constexpr` для піна й інтервалу | `config.h` | `config::LED_PIN`, `config::BLINK_INTERVAL_MS` |
| 1. Мінімум глобальних змінних | `main.cpp` | `led` (потрібна і в `setup()`, і в `loop()`), `buttonEdge` (ISR ↔ `loop()`) і демонстраційний лічильник `isrCalls`. Решта стану - `static` всередині функцій |
| 1. Без `delay()`, `millis()` у superloop | `updateLed()` | `nowMs - lastToggleMs >= BLINK_INTERVAL_MS` |
| 1. «Клас Led з `init()` і `set()`» | `led.h` | `struct Led` + `ledInit()`, `ledSet()`, див. нижче |
| 2. Структура конфігурації зі `static const` / `constexpr` | `config.h` | `namespace config` з `constexpr`. Жодного числа в логіці |
| 3. Час ітерації, вивід кожні 1000 ітерацій | `updateLoopStats()` | Середнє за блок 1000 ітерацій + максимум. Друк не частіше 1 разу на секунду |
| 4. Кнопка через `attachInterrupt` | `armButtonInterrupt()`, `onButtonFalling()` | `FALLING`, ISR лише ставить `volatile bool` |
| 4. Режими по колу | `nextMode()` | `switch` по `enum class LedMode` |
| 4. Debounce і логіка в `loop()` | `pollButtonPress()` | Автомат станів: після першого фронту `detachInterrupt()` на 30 мс, підтвердження за рівнем піна, повернення переривання після стабільного відпускання |

## Що в коді і чому так

### Led без класу

Умова просить клас `Led` з `init()` і `set()`. Те саме можна зробити без ООП: дані в `struct Led { pin; state; }`, поведінка у вільних функціях `ledInit(Led&)`, `ledSet(Led&, LedState)`, `ledToggle(Led&)`. Функції `inline` у заголовку, тож компілятор зазвичай вбудовує їх прямо в місце виклику, і накладних витрат немає.

Аналогія: struct - це паспорт пристрою (номер піна, поточний стан), а функції - інструкція, як з ним працювати. Інструкцію не обовʼязково вшивати в паспорт.

Студентські роботи з класом приймаються. Тоді в рев'ю дивимось, щоб клас був «легким»:
- без `virtual`, якщо немає кількох реалізацій (кожен віртуальний клас тягне vtable, а виклик іде через вказівник);
- `pinMode()` у `init()`, а не в конструкторі. Глобальний обʼєкт конструюється до `setup()`, а для периферії порядок ініціалізації тоді неочевидний (лекція, розділ 5: «без складної логіки в конструкторах»);
- конструктор `constexpr`, без `new` усередині;
- `static constexpr` члени класу-конфігурації в C++11 (Arduino-ESP32 2.x збирає з `gnu++11`) не можна передавати за посиланням без визначення поза класом, інакше linker error `undefined reference`. `namespace` з `constexpr` цієї пастки не має.

### `namespace config` замість `#define`

`constexpr uint8_t LED_PIN = 4;` має тип, область видимості й обчислюється при компіляції, тому не займає RAM. `#define LED_PIN 4` - просто текстова підстановка: без типу, без області видимості, і в дебагері його не видно. `namespace` дає префікс `config::`, по якому в коді одразу видно, що це налаштування, а не робоча змінна.

### `volatile bool` і коли скидати прапор

`buttonEdge` пише ISR, а читає `loop()`. Без `volatile` компілятор з `-Os` має право прочитати змінну один раз і крутити цикл з копією в регістрі. Це показано в практиці 2.1, крок 2 (там є і дизасемблер).

Шаблон з лекції `if (flag) { flag = false; ... }` має маленьке вікно: між читанням і скиданням може прийти ще одне переривання, і його скидання затре. Тут цього вікна немає: прапор скидається в `armButtonInterrupt()` тоді, коли переривання вимкнене, тобто ISR у цей момент фізично не може його записати. Тому `volatile bool` тут повністю достатньо.

### Антибрязкіт: відключаємо переривання

Кожен «стрибок» контакту - це окремий фронт, а значить окремий виклик ISR. Одне натискання дає 5-20 переривань (урок 1.5), зношена кнопка чи повільний фронт - сотні. Кожне переривання забирає процесор у `loop()`, а на рівні системи це «шторм переривань»: процесор зайнятий обробкою брязкоту замість корисної роботи.

Тому після першого фронту переривання вимикаємо, і далі брязкіт процесор взагалі не турбує. `pollButtonPress()` - невеликий автомат станів:

| Стан | Переривання | Що робимо | Перехід |
|---|---|---|---|
| `Armed` | увімкнене | чекаємо `buttonEdge` | прапор є → `detachInterrupt()` → `Confirming` |
| `Confirming` | вимкнене | чекаємо `PRESS_LOCKOUT_MS` = 30 мс, поки брязкіт натискання вщухне | читаємо рівень: `LOW` → подія «натиснули», `HIGH` → завада. В обох випадках → `WaitRelease` |
| `WaitRelease` | вимкнене | polling рівня: кожен `LOW` перезапускає відлік | `HIGH` протримався `RELEASE_QUIET_MS` = 30 мс → скинути прапор, `attachInterrupt()` → `Armed` |

Аналогія: дзвінок у двері. Почув дзвінок - вимкнув його і пішов глянути, чи справді хтось прийшов. Дочекався, поки гість зайде і двері зачиняться, і лише тоді ввімкнув дзвінок знову. Поки ти йдеш до дверей, нетерплячий гість може тиснути кнопку скільки завгодно, але дзвінок мовчить.

Чому не просто «вимкнути на 30 мс і ввімкнути назад»: якщо тримати кнопку довше за 30 мс (а людина тримає 100-300 мс), переривання вже буде увімкнене в момент відпускання. Брязкіт відпускання дасть спадні фронти, і ISR сприйме їх як нове натискання. Тому переривання повертаємо, лише коли кнопка стабільно відпущена. Це та сама помилка з уроку 1.5: «забули про відпускання».

Деталі, на які варто звернути увагу:
- `detachInterrupt()` викликається в `loop()`, а не в ISR. ISR лишається мінімальною (як вимагає умова), а за мікросекунди, поки `loop()` дійде до відключення, проскочить хіба 1-2 зайві виклики. Лічильник `isrCalls` у виводі це показує.
- В Arduino-ESP32 `detachInterrupt()` викликає `gpio_isr_handler_remove()`, а та вимикає переривання піна (`gpio_intr_disable`). Тобто брязкіт справді не доходить до процесора, а не просто обробляється «порожнім» обробником.
- Перевірка рівня в `Confirming` захищає від двох речей одразу: від завади на дроті (короткий імпульс без натискання) і від «застарілого» фронту, що міг спрацювати одразу після повторного `attachInterrupt()`. В обох випадках пін `HIGH`, і подія відкидається.
- Обидва часи по 30 мс = 2-3 × максимального брязкоту з уроку 1.5, а не середнього. Якщо кнопка брязкотить десятки мілісекунд, треба перевірити контакт у макетці, а не збільшувати час.
- Реакція: режим перемикається через 30 мс після натискання. Людина таку затримку не помічає (поріг відчуття ~100 мс).

### Вимірювання superloop

- Середнє рахується як час блоку з 1000 ітерацій, поділений на 1000. Міряти кожну ітерацію окремо і усереднювати менш точно: `micros()` має крок 1 мкс, а ітерація може бути коротшою.
- Максимум найдовшої окремої ітерації важливіший за середнє: саме він визначає найгірший час реакції. Він більший за середнє через переривання (тік FreeRTOS, USB/UART) і через друк режиму в Serial.
- Блок із 1000 ітерацій проходить за мілісекунди. Друк кожного блоку дав би сотні рядків за секунду, і сам `Serial` почав би гальмувати цикл, який ми міряємо. Тому блоки рахуються, як просить умова, а друкується не частіше раза на секунду. Час самого `printf` у наступний блок не потрапляє.
- `×1000` для наносекунд робиться в `uint64_t`, бо `uint32_t` переповниться на довгих блоках.
- Різниця `micros()` беззнакова, тож переповнення раз на ~71 хв не страшне. Те саме з `millis()` (~49,7 доби).

### Зміна режиму

При перемиканні вихід одразу виставляється під новий режим, тож LED не «залипає» у старому стані (помилка з 1.4). Блимання стартує зі стану On, щоб реакцію на кнопку було видно одразу.

- README: таблиця підключень (пін → компонент → резистор) з розрахунком резистора.

## Пастки (Trust No Pin)

- Кнопка в `INPUT` без підтяжки: пін «плаває», режими перемикаються від руки поруч.
- Перевірка `== HIGH` з pull-up: логіка інвертована, натиснута = `LOW`.
- `FALLING` + debounce «від першого фронту»: відпускання інколи рахується як натискання.
- `detachInterrupt()` на фіксований час без перевірки відпускання: та сама проблема, якщо тримати кнопку довше за цей час.
- `detachInterrupt()` / `attachInterrupt()` усередині ISR: в Arduino-ESP32 це не ISR-безпечні функції (вони реєструють обробник у сервісі переривань).
- Debounce у самій ISR (`if (millis() - last > 30)`): брязкіт фільтрується, але шторм переривань лишається, ISR все одно викликається на кожен стрибок.
- ISR без `IRAM_ATTR`: падає, щойно флеш зайнятий (запис NVS, OTA).
- `Serial.print` в ISR: виклик блокується на UART і може зламати систему.
- Друк на кожній ітерації чи на кожному блоці: вимірювання міряє швидкість UART, а не логіку.
- `int`/`#define` замість `constexpr uintN_t`; `String` для назви режиму замість `const char*` на рядок-літерал у флеші.

### Помилки з перевірених робіт 2.1

- Обʼєкт стає валідним лише після `begin()` / `start()`, а виклик забули. Глобальні змінні обнулені, тож у таймера період 0, і він «спрацьовує» на кожному проході: два LED перемикаються сотні тисяч разів на секунду і виглядають тьмяно ввімкненими. Захист в еталоні: дані ініціалізуються константами одразу при оголошенні (`static Led led = {config::LED_PIN, LedState::Off};`), а `static_assert` у `config.h` не дасть зібрати прошивку з нульовим періодом.
- Debounce лише за часом: «прийняти фронт, якщо від минулого натискання минуло ≥ 50 мс». Брязкіт при відпусканні кнопки, яку тримали довше за 50 мс, перемикає режим удруге. В еталоні натискання підтверджується рівнем піна, а переривання повертається лише після стабільного відпускання.
- Звіт часу циклу на кожен блок із 1000 (або 10 000) ітерацій: це десятки-сотні рядків за секунду. В еталоні блоки рахуються, але друк не частіше раза на секунду.
- Міряється лише частина `loop()` (від `micros()` на початку до кінця корисної роботи). Накладні витрати Arduino між проходами у вимір не потрапляють. В еталоні міряється різниця між початками сусідніх проходів.
- Стан LED зберігається окремо від LED (глобальна `ledState` поруч з обʼєктом, який знає лише пін): два джерела правди. В еталоні стан живе в `struct Led`.
- Після повернення в Блимання LED вимикається і загоряється лише через період: секунду немає видимої реакції на кнопку. В еталоні блимання стартує з `On`.
- Немає README з підключенням і логу Serial, хоча умова просить «код і результат виконання».

## 🚀 На виріст (поза програмою модуля)

- `std::atomic<bool>` і `buttonEdge.exchange(false)`: «прочитати й скинути» однією неподільною операцією. Тут не потрібно, бо прапор скидається при вимкненому перериванні. Але там, де переривання не вимикають, це правильний шаблон (практика 2.1, крок 6).
- Debounce без переривань, чистим polling раз на 1-5 мс, теж промисловий варіант: шторму переривань немає за визначенням, а реакція 1-5 мс для людини миттєва.
- Апаратний антибрязкіт: RC-фільтр (наприклад, 10 кОм + 100 нФ, τ = 1 мс) + вхід із тригером Шмітта. Тоді брязкіт не доходить навіть до GPIO.
- В ESP-IDF замість detach/attach: `gpio_intr_disable()` / `gpio_intr_enable()` - легші виклики, бо не перереєстровують обробник. А з RTOS ISR будить задачу через `xTaskNotifyFromISR()`, і задача робить те саме, що тут `loop()`.
- Замість «крутитись» мільйони разів на секунду можна присипляти ядро до наступної події (`vTaskDelay` / light sleep). Це економія енергії, тема RTOS і живлення.
- В ESP-IDF той самий драйвер: `gpio_config_t` однією структурою (підхід «таблиця конфігурації» з розділу 5 лекції) і `gpio_isr_handler_add()`.
