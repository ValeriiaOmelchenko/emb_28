# Практика 6.3 (спрощена) - FreeRTOS: черги

Спрощений варіант `6_3_Practice`: три кроки, по одній ідеї в кожному, менше «промислових» деталей. Живий код до уроку 6.3. Спершу ламаємо: дві задачі на двох ядрах ESP32-S3 інкрементують спільний лічильник і гублять частину інкрементів. Потім лагодимо чергою: у лічильника один власник. Наостанок - подія з переривання кнопки через чергу. Плата ESP32-S3-DevKitC-1, PlatformIO, `framework = espidf`, чистий C17.

| Крок | Середовище | Файл | Що показує |
|---|---|---|---|
| 1 | `step1` | `src/step1_race.c` | гонка на `s_counter++` з двох ядер; `volatile` не рятує |
| 2 | `step2` | `src/step2_queue.c` | той самий лічильник через `xQueue`: один власник, нічого не губиться |
| 3 | `step3` | `src/step3_isr_queue.c` | ISR кнопки BOOT -> черга -> задача; антибрязкіт через вимкнення переривання |

```bash
pio run -e step1 -t upload -t monitor
```

Файл кроку вибирає `src/CMakeLists.txt` за назвою середовища (як у `6.1/6_1_Practice`). `sdkconfig.defaults` ставить тік 1 мс.

Нічого підключати не треба: кнопка BOOT на платі (GPIO0, натиснута = 0). Не тримай її під час ресету - плата зайде в режим прошивки.

## Крок 1 - гонка

Задачі `inc_A` (ядро 0) і `inc_B` (ядро 1) роблять `s_counter++` мільйон разів кожна. Повторити - RST.

Що проговорити:
- `++` - це три дії: прочитати, додати, записати. Двоє касирів бачать у зошиті «10», кожен продає по товару і записує «9».
- `volatile` - «щоразу ходи в памʼять», але не атомарність. Тут він навмисно.
- Результат щоразу інший: на столі «працює», у полі - ні.
- Фініш: `_Atomic` лічильник `s_done` (`atomic_fetch_add`) - той самий «++», але неподільний. Окрема змінна: дані і прапорець «готово» не змішуємо.
- Пріоритет задач = пріоритету `app_main` (1), тому створена задача не витісняє `app_main`, і обидві стартують разом.

Експеримент: `TASK_B_CORE 0`. Обидві задачі на одному ядрі ділять його по тіках. Втрат значно менше (можуть бути й нулі), але вони трапляються: гонці досить витіснення між «прочитати» і «записати».

Очікуваний вивід (числа щоразу різні):

```
I (...) step1_race: === Гонка: 2 задачі x 1000000 інкрементів, ядра 0 і 1, лічильник volatile ===
W (...) step1_race: Лічильник 1xxxxxx з 2000000, втрачено xxxxxx, час xx мс
```

### Експеримент з `_Atomic`

Поставити `USE_ATOMIC 1`. Рядок `s_counter++` не змінюється, змінюється лише тип: `static _Atomic uint32_t s_counter;`.

Що проговорити:
- Для `_Atomic`-змінної компілятор сам робить з `++` атомарний `atomic_fetch_add` (C17, 6.5.2.4). Тепер щоразу рівно 2000000.
- Ціна: на S3 атомарний інкремент - цикл з `S32C1I` (compare-and-swap). Якщо інше ядро встигло змінити значення, спроба повторюється. Порівняти час у лозі з варіантом `volatile`.
- Підступність: атомарність «прихована» в типі. Явний `atomic_fetch_add(&s_counter, 1)` читається краще - одразу видно, що операція особлива.
- Атомарність працює для однієї змінної. Якщо треба узгоджено змінити дві змінні (лічильник і суму), `_Atomic` не допоможе - потрібна черга (крок 2) або мʼютекс.

```
I (...) step1_race: === Гонка: 2 задачі x 1000000 інкрементів, ядра 0 і 1, лічильник _Atomic ===
W (...) step1_race: Лічильник 2000000 з 2000000, втрачено 0, час xx мс
```

## Крок 2 - черга

`prod_A` (ядро 0) і `prod_B` (ядро 1) по 10 000 разів кладуть у чергу свій номер. `consumer` (пріоритет вище) виймає і рахує.

Що проговорити:
- Гонку прибрали не замком, а архітектурою: лічильник - локальна змінна однієї задачі. Черга копіює дані і всередині захищена, тому безпечна між задачами і ядрами.
- Порядок ініціалізації: черга -> задачі.
- Consumer важливіший за продюсерів: щойно щось лягло в чергу, він забирає.
- Таймаути замість `portMAX_DELAY`: продюсер рахує втрати, а не висить навіки; consumer по тиші розуміє, що продюсери закінчили, і друкує підсумок.

```
I (...) step2_queue: Продюсер 0 (ядро 0): втрачено 0
I (...) step2_queue: Продюсер 1 (ядро 1): втрачено 0
I (...) step2_queue: Лічильник 20000 з 20000 (A: 10000, B: 10000)
```

## Крок 3 - ISR і черга

| Хто | Що робить |
|---|---|
| `button_isr` | на першому спадному фронті вимикає своє переривання, кладе тік натискання в чергу (`xQueueSendFromISR`), `portYIELD_FROM_ISR` |
| `button_task` | бере подію з черги, логує, чекає 50 мс стабільного відпускання, скидає статус і вмикає переривання |

Що проговорити:
- ISR мінімальний: без логів, лише `...FromISR`, `IRAM_ATTR`. Усе повільне - у задачі.
- Порядок: черга -> задача -> переривання. Інакше натискання на старті дасть `xQueueSendFromISR(NULL)` і assert.
- Антибрязкіт: перший фронт - вже натискання, ISR вимикає себе, брязкіт до процесора не доходить. Назад вмикає задача після відпускання. Аналогія: почув дзвінок - вимкнув дзвінок і пішов відчиняти; увімкнув, коли гість прибрав палець.
- Trust No Pin: `gpio_intr_disable` вимикає лише доставку, фронти брязкоту все одно лягають у регістр статусу. Тому перед `gpio_intr_enable` - `gpio_ll_clear_intr_status`, інакше одразу хибне «натискання».
- Чому ISR не перевіряє результат відправки: поки переривання вимкнене, у черзі максимум одна подія.

```
I (...) step3_isr: === ISR -> черга: натискай BOOT ===
I (...) step3_isr: BOOT #1 (t=... мс)
```

## 🚀 На виріст

- `xQueueCreateStatic()` - черга в статичних буферах, без heap.
- Кнопка і потік даних в одній черзі: тривогу на початок - `xQueueSendToFrontFromISR`, або окрема черга / Queue Set.
- Одна задача-отримувач і одне значення - task notification легша за чергу.
- «Останнє значення» замість потоку - черга довжиною 1 і `xQueueOverwrite()`.
- Критична секція `portMUX` - захист кількох змінних разом, тема мʼютексів і spinlock.
