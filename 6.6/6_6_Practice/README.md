# Практика 6.6 - енергозбереження: Active, Light Sleep, Deep Sleep, джерела пробудження

Код для живої демонстрації на уроці 6.6. Кроки йдуть за планом уроку. Плата ESP32-S3-DevKitC-1, PlatformIO, `framework = espidf`, чистий C17: процедурно, без динамічної памʼяті.

| Крок | Середовище | Файл | Що показує | Час |
|---|---|---|---|---|
| 1 | `step1` | `src/step1_active.c` | Active: обидва ядра на 240 МГц рахують, вимір струму | 7 хв |
| 2 | `step2` | `src/step2_light_sleep.c` | `esp_light_sleep_start()`: таймер + кнопка, локальні змінні живі | 8 хв |
| 3 | `step3` | `src/step3_deep_sleep.c` | Deep Sleep: `RTC_DATA_ATTR` росте, звичайна змінна щоразу 1 | 8 хв |
| 4 | `step4` | `src/step4_ext0_timer.c` | два джерела пробудження: EXT0 (кнопка) + таймер | 8 хв |
| 5 | `step5` | `src/step5_wakeup_cause.c` | «спочатку причина, потім дія»: розгалуження за причиною | 7 хв |
| 6 | `step6` | `src/step6_busy_wait.c` | автоматичний Light Sleep (PM + tickless): busy-wait проти `vTaskDelay` | 5 хв |

```bash
pio run -e step1 -t upload -t monitor
```

`pio run` без `-e` збирає лише `step1` (`default_envs`). Файл кроку вибирає `src/CMakeLists.txt`: середовище `stepN` збирає лише `src/stepN_*.c`. Для всіх кроків увімкнено `-Wextra -Wshadow -Wstrict-prototypes`. Спільне (пін кнопки, `wait_button_released()`, `console_flush()`) - у `include/practice.h`.

`sdkconfig.defaults` (спільний для всіх кроків): CPU 240 МГц (за замовчуванням 160), `CONFIG_PM_ENABLE`, `CONFIG_FREERTOS_USE_TICKLESS_IDLE`, `CONFIG_PM_PROFILING`. Без виклику `esp_pm_configure()` PM нічого не вмикає, тому автоматично засинає лише крок 6. Якщо змінюєш `sdkconfig.defaults` - видали `sdkconfig.stepN`, інакше PlatformIO візьме старий.

Перемикачі на початку файлів (змінити, прошити знову):

| Файл | Перемикач | Значення |
|---|---|---|
| `step1_active.c` | `BUSY_CORES` | 2 / 1 - скільки ядер рахують, 0 - обидві задачі в Blocked |
| `step6_busy_wait.c` | `BUSY_WAIT` | 0 - `vTaskDelay` (чип спить), 1 - busy-wait (не спить) |

Версія ESP-IDF. PlatformIO тут збирає ESP-IDF 6.1, а методичка написана під v5.5.4. У 6.x `esp_sleep_get_wakeup_cause()` deprecated: якщо два джерела спрацюють майже одночасно, вона повертає лише одне. Замінник `esp_sleep_get_wakeup_causes()` повертає бітову маску `BIT(ESP_SLEEP_WAKEUP_x)`, тому в коді `if` на кожен біт, а не `switch`. Для v5.5 `switch (esp_sleep_get_wakeup_cause())` з методички коректний.

## Підключення

| Що | Куди |
|---|---|
| тактова кнопка | GPIO4 - кнопка - GND (кроки 2, 4, 5) |
| USB-кабель | у порт UART на DevKitC-1 (не USB) |
| мультиметр (мА) | у розрив живлення, див. нижче |

Кнопку BOOT (GPIO0) навмисно не беремо. GPIO0 - strapping-пін: у виробі на ньому датчик пробудження не вішають. GPIO4 - RTC GPIO (на S3 це GPIO 0-21), тому працює і з EXT0 у Deep Sleep. Підтяжка внутрішня (~45 кОм); для довгого дроту або реального пристрою - зовнішній 10 кОм до 3V3 (Trust No Pin).

Чому порт UART. Консоль ESP-IDF за замовчуванням на UART0, а міст USB-UART живиться від USB і переживає сон чипа: монітор не відвалюється. Через нативний порт USB (USB-Serial-JTAG) у Deep Sleep USB-пристрій зникає з компʼютера, монітор доведеться перепідключати.

### Як міряти струм (Trust No Pin)

Мультиметр у розриві USB (або USB-тестер) бачить струм усієї плати: LDO, світлодіод живлення, міст USB-UART. Тому:
- різницю Active / Light Sleep видно добре (десятки мА проти одиниць мА);
- мкА Deep Sleep так не побачиш: плата сама споживає більше, ніж чип у сні. Падіння буде помітне, але до «підлоги» плати, а не до 7-8 мкА з datasheet.

Чесно виміряти чип: живити плату з лабораторного БЖ 3,3 В на пін 3V3 через мультиметр (USB від'єднано), а лог дивитись через зовнішній USB-UART на TX0/RX0. На уроці цього не робимо, але проговорюємо.

Цифри для орієнтиру (ESP32-S3 Datasheet, розділ 5, Table 5-9 і 5-10):

| Режим | Datasheet | Що було в методичці |
|---|---|---|
| Active з Wi-Fi TX | 283-340 мА пік | ~240 мА |
| CPU 240 МГц без радіо | 33-108 мА (залежить від навантаження) | - |
| Light Sleep | 240 мкА (+140 мкА Octal PSRAM на N16R8) | ~0,8 мА |
| Deep Sleep (RTC памʼять) | 7-8 мкА | 10-150 мкА |
| Power off (CHIP_PU = 0) | 1 мкА | Hibernation ~5 мкА |

Повна таблиця розбіжностей з посиланнями - у `../6_6_Theory/index.html`.

## Крок 1 - Active

Дві задачі, по одній на ядро, секунду рахують без зупинки, друкують кількість раундів і віддають 1 тік Idle Task.

```
I (310) active: CPU 240 МГц, ядер зайнято: 2. Дивись на мультиметр.
I (1320) active: ядро 0: 21734 раундів за 1000 мс (seed 1c2a...)
I (1320) active: ядро 1: 21741 раундів за 1000 мс (seed 1c2a...)
```

(числа - ілюстрація)

Що проговорити:
- Записати струм при `BUSY_CORES` 2, 1, 0. Це наша «стеля» для порівняння в наступних кроках.
- `BUSY_CORES 0`: задачі в Blocked, але струм все одно мА-рівня. Без Power Management ядро просто чекає переривання на 240 МГц, тактування не вимикається. Blocked - це передумова сну, а не сам сон (повернемось у кроці 6).
- Навіщо `vTaskDelay(1)` після секунди роботи: інакше Idle Task на ядрі не отримує CPU, і через 5 с спрацює Task Watchdog.
- Без радіо. З Wi-Fi пікові струми в кілька разів вищі, і саме вони визначають, яке живлення ставити (LDO, конденсатори).

## Крок 2 - Light Sleep

`app_main` у циклі засинає на 5 с через `esp_light_sleep_start()`. Будить таймер або кнопка на GPIO4. Після пробудження друкує, скільки спала, причину і локальний лічильник `wake_no`.

```
I (5320) light: #1: прокинулась через 5000 мс, причина: таймер. wake_no не загубився
I (6870) light: #2: прокинулась через 1540 мс, причина: кнопка. wake_no не загубився
```

Що проговорити:
- Аналогія: Light Sleep - людина задрімала з книжкою в руках, прокинулась і читає з того ж рядка. Тактування digital-домену вимкнено, живлення лишилось: RAM, регістри, стеки задач FreeRTOS - усе на місці.
- `wake_no` - локальна змінна на стеку, і вона росте. Виконання продовжується з наступного рядка після `esp_light_sleep_start()`. Порівняти з кроком 3.
- Струм на мультиметрі падає до одиниць мА (на DevKit). Час пробудження - порядку мілісекунд.
- `console_flush()` перед сном: `fflush(stdout)` + `uart_wait_tx_idle_polling()`. Без цього останній рядок обрізається, бо UART не встиг його вивести.
- GPIO-пробудження в Light Sleep - лише за рівнем. Якщо кнопку тримати, чип засне і миттю прокинеться знову. Тому після пробудження кнопкою чекаємо відпускання з таймаутом: залипла кнопка не має назавжди відібрати в пристрою сон.

## Крок 3 - Deep Sleep

Таймер будить кожні 5 с. На кожному старті збільшуються дві змінні: `s_boot_count` з `RTC_DATA_ATTR` і звичайна `s_ram_count`.

```
I (305) deep: app_main() з початку. reset reason = 8 (пробудження з Deep Sleep)
I (305) deep: RTC_DATA_ATTR s_boot_count = 4, звичайна s_ram_count = 1
```

Що проговорити:
- У моніторі кожні 5 с - повний лог завантажувача. Deep Sleep знеструмлює digital-домен, пробудження = reset, `app_main()` з першого рядка.
- `s_ram_count` завжди 1: звичайна RAM після сну обнуляється. `s_boot_count` живе в RTC SRAM, яка живиться і уві сні.
- Три способи зберегти дані: `RTC_DATA_ATTR` (швидко, без зносу, але зникає при знятті живлення), NVS у flash (переживає зняття батареї, повільніше, ресурс записів обмежений), зовнішня памʼять. Натиснути RESET: `s_boot_count` теж обнулиться (холодний старт).
- На N16R8 PSRAM у Deep Sleep вимикається: дані «на після сну» туди не кладемо.
- Рядок після `esp_deep_sleep_start()` ніколи не виконається.

## Крок 4 - EXT0 + таймер

Deep Sleep з двома джерелами: таймер 10 с і кнопка (EXT0, рівень 0). Після старту друкуємо сиру маску причин.

```
I (305) ext0: старт #3, маска причин = 0x00000004 (TIMER = bit 4, EXT0 = bit 2)
```

(номери бітів - з `esp_sleep_wakeup_cause_t`, у лозі будуть фактичні)

Що проговорити:
- Джерела пробудження налаштовуються до `esp_deep_sleep_start()` і комбінуються: прокинемось від того, що настане раніше.
- EXT0 стежить за піном без CPU: це робить RTC-контролер. Тому пін - лише RTC GPIO, а підтяжка - RTC-шна (`rtc_gpio_pullup_en`). Звичайна GPIO-підтяжка належить digital-домену і в Deep Sleep вимкнена. Без підтяжки вхід плаває - і чип прокидається від наведень.
- EXT0 - один пін. Кілька пінів - EXT1 з бітовою маскою.
- Пробудження за рівнем + кнопку тримають = цикл перезавантажень. Тому перед сном `wait_button_released()` з таймаутом, і якщо кнопка залипла - засинаємо лише з таймером.

## Крок 5 - причина пробудження

Той самий сон, що в кроці 4, але `app_main()` спершу дивиться на причину і розгалужується: перший старт / таймер / кнопка / неочікуване. Лічильники таймерних і кнопкових пробуджень - у `RTC_DATA_ATTR`.

```
I (305) cause: перший старт (reset reason = 1): ініціалізація
I (305) cause: таймер: планове пробудження #1
W (305) cause: кнопка: позапланова подія #1 (таймерних було 1)
```

Що проговорити:
- Аналогія: задзвонив телефон - спершу дивишся, хто дзвонить (будильник чи начальник), потім вирішуєш, що робити. У Deep Sleep програма не памʼятає, чому заснула і чому прокинулась.
- Гілка «перший старт» обовʼязкова: після подачі живлення RTC SRAM обнулена, тут ініціалізуємо стан.
- Гілка «неочікувана причина» - лог помилки, а не мовчазний ігнор.
- Маска, а не одне значення: таймер і кнопка можуть спрацювати майже одночасно, `switch` по одному значенню одну з подій загубить (див. «Версія ESP-IDF» вище).
- Якби був Wi-Fi: `esp_wifi_stop()` перед сном, і після пробудження зʼєднання встановлюється заново.

## Крок 6 - busy-wait проти vTaskDelay

`esp_pm_configure()` з `light_sleep_enable = true`: тепер Idle Task сама кладе чип у Light Sleep, щойно всі задачі в Blocked. Задача 100 мс «працює», потім 2 с чекає. Кожні 5 циклів `esp_pm_dump_locks()` друкує, скільки часу чип був у кожному режимі.

```
Mode stats:
  SLEEP    ...    9634ms  94%      <- BUSY_WAIT 0
  CPU_MAX  ...     532ms   5%
```

(з `BUSY_WAIT 1` рядок SLEEP близький до 0%)

Що проговорити:
- Код задачі однаковий, різниця лише в тому, як вона чекає. `vTaskDelay` - задача в Blocked, CPU вільний, Idle Task засинає. `while (час не вийшов) {}` - задача Running, Idle Task не запускається, сну немає, струм як у кроці 1.
- Чип засинає, лише коли обидва ядра в Idle. Один busy-wait на одному ядрі - і сну немає для всіх.
- Чотири способи правильно чекати: `vTaskDelay`, task notification, `xSemaphoreTake`, `xQueueReceive` (усе з 6.5). Усі переводять задачу в Blocked.
- Порівняти з кроком 2: там ми спали вручну, тут ОС спить сама між подіями, а код задач про сон не знає взагалі.
- Чому `WAIT_MS` < 5 с: довший busy-wait ще й розбудить Task Watchdog (Idle Task не отримує CPU).

## Навмисно не включено (це домашка)

- зчитування АЦП і журнал відліків;
- лічильник планових перевірок, який друкується і скидається за тригером;
- окрема задача FreeRTOS, що після тригера «встановлює зʼєднання» і на 4 с засинає в Light Sleep посеред задачі;
- поєднання всього в один логер.

Кроки 2-5 дають цеглинки (Light Sleep у задачі, Deep Sleep, EXT0 + таймер, причина пробудження), скласти їх у логер - завдання студентів.

## 🚀 На виріст

- ULP-копроцесор: опитує датчик у Deep Sleep і будить CPU лише за порогом. Деталі - на сторінці теорії.
- `rtc_gpio_isolate()` для невикористаних RTC-пінів перед Deep Sleep: прибирає витоки через зовнішні підтяжки.
- `esp_pm_lock_create()`: тимчасово заборонити сон або зниження частоти на час, коли периферії потрібна стабільна тактова (напр. під час обміну по SPI).
